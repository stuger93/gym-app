# Seguridad — Gym App

Este documento resume las medidas de seguridad implementadas en el proyecto y las mejoras identificadas que aún no se implementaron, con el criterio usado para priorizarlas. Se actualiza a medida que el proyecto avanza.

## Medidas implementadas

- **Hash de contraseñas (bcrypt vía passlib)**: ninguna contraseña se guarda en texto plano. `backend/app/auth.py` usa `passlib.context.CryptContext` con el esquema `bcrypt` tanto para generar el hash al crear un usuario como para verificarlo en el login.
- **Sesión vía cookie `httpOnly`**: el JWT de sesión se setea como cookie `httpOnly` en la respuesta de `POST /login` y nunca se expone en el body de la respuesta ni se guarda en `localStorage`, por lo que un script inyectado vía XSS no puede leerlo. Ver [ADR-001](docs/adr/001-cookie-httponly-vs-localstorage.md).
- **CORS restrictivo**: `CORSMiddleware` está configurado con `allow_origins=[FRONTEND_ORIGIN]` (un origen explícito leído de variable de entorno) y `allow_credentials=True`, nunca con `"*"`. Esto es obligatorio para que las cookies de sesión funcionen entre el frontend y el backend, y evita que cualquier origen arbitrario pueda hacer requests autenticados.
- **Rate limiting en `/login`**: usando `slowapi`, `POST /login` está limitado a 5 intentos por minuto por IP. Mitiga ataques de fuerza bruta y de enumeración de contraseñas contra el endpoint de autenticación.
- **Mensajes de error genéricos**: tanto si el email no existe como si la contraseña es incorrecta, `/login` responde siempre `401 {"detail": "Credenciales inválidas"}`. No se revela cuál de los dos campos falló (evita que un atacante pueda enumerar qué emails están registrados), y ningún endpoint devuelve stack traces ni detalles internos al cliente.
- **Validación de input con Pydantic**: `LoginRequest` valida formato de email y tipos antes de que el dato llegue a la capa de base de datos, en todos los endpoints que reciben body.
- **Serialización explícita de salida**: `UsuarioOut` (Pydantic) define exactamente qué campos de `Usuario` se devuelven en las respuestas; `password_hash` nunca se serializa ni se expone en ninguna respuesta de la API.
- **Queries parametrizadas (SQLAlchemy ORM)**: todo acceso a la base de datos pasa por el ORM (`db.query(...)`, `db.get(...)`), sin concatenación manual de SQL, eliminando la clase de vulnerabilidad de SQL injection.
- **Secretos fuera del código**: `JWT_SECRET_KEY`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` y el resto de la configuración sensible viven en variables de entorno (`.env`, nunca commiteado); `.env.example` documenta qué variables existen sin exponer valores reales.
- **Seed de admin sin credenciales hardcodeadas**: `backend/app/seed.py` crea el primer usuario admin leyendo `ADMIN_EMAIL`/`ADMIN_PASSWORD` de entorno, de forma idempotente, y nunca se ejecuta automáticamente al levantar el contenedor (evita resets accidentales de la contraseña del admin).

## Mejoras identificadas, no implementadas aún

- **Token CSRF explícito**: hoy la protección contra CSRF depende únicamente de `SameSite=Lax` en la cookie de sesión, que bloquea el envío de la cookie en la mayoría de los requests cross-site iniciados por terceros pero no cubre todos los escenarios (por ejemplo, algunos requests `GET` de nivel superior siguen adjuntando la cookie). Se priorizó no implementar un token CSRF dedicado en esta rebanada porque el sistema todavía no maneja pagos ni datos críticos, y el único endpoint mutante protegido es `/login` (que además ya tiene rate limiting). **Se implementará antes de manejar pagos reales o de un despliegue a producción**, momento en el que el costo de un ataque exitoso deja de ser aceptable.
- **`secure=true` en la cookie de sesión solo bajo HTTPS**: en desarrollo local `COOKIE_SECURE=false` porque el sitio corre sobre HTTP. Antes de cualquier despliegue a un entorno accesible públicamente, `COOKIE_SECURE` debe pasar a `true` y el tráfico debe servirse exclusivamente por HTTPS (si no, la cookie viajaría en texto plano). Queda como ítem obligatorio del `deploy-checklist`.
- **Rotación de `JWT_SECRET_KEY`**: hoy el secreto es estático por entorno. No hay todavía un mecanismo de rotación ni de invalidación masiva de sesiones (por ejemplo, ante sospecha de compromiso del secreto). Se evaluará cuando el proyecto tenga más de un usuario activo real y el costo de forzar un re-login masivo sea menor al riesgo de no poder rotar.
- **Rate limiting distribuido**: el límite de `/login` se guarda en memoria del proceso (vía `slowapi`), lo cual es correcto mientras haya una sola instancia del backend. Si el despliegue pasa a tener múltiples réplicas, hace falta un backend compartido (ej. Redis) para que el límite sea efectivo entre instancias.
- **Autorización por rol en endpoints futuros**: hoy existe el campo `rol` en `usuarios` y la dependency `get_current_user`, pero todavía no hay endpoints que necesiten distinguir permisos entre roles (solo existe `admin`). Cuando se agreguen roles adicionales (instructor, recepción), habrá que construir una dependency de autorización (`require_rol(...)`) reusando `get_current_user` como base.
